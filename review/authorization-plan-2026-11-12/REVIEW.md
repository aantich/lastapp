# Lastapp Authorization Plan Review

**12 November 2026 — design review record.** The subsequently approved identity/roles/scopes foundation is implemented in [FOUNDATION.md](../../FOUNDATION.md). Entity ACLs, the data runtime and SDK remain deferred; code descriptions below record the state reviewed before implementation.

The architecture is coherent: one global identity/authorization registry, fixed Tenant/team roles, Space-owned business definitions, and Apps that inherit or narrow Space authority. The review corrected ambiguities in permission composition, delegation, publication and implementation order. Lastapp is undeployed; the plan therefore updates the development schema and fixtures directly. The [revised implementation plan](../../SPACE_AUTHORIZATION_PLAN.md) is the canonical proposal.

The findings below are design risks and required implementation changes. Their resolution in the plan does not mean that the new authorization/entity runtime has been implemented or security-tested.

## Findings and resolutions

| High | Independent Space/App allow unions can combine Space permission Q with an App permission based on P. That loses the intended base permission’s activation and restrictions. The written AND/OR formula also lacked explicit grouping. | Preserve one base permission throughout each path, parenthesize the Space allow/share union, and reject cross-matched paths. A write needs one complete path; read fields each need a complete path. Sections 3 and 12. |
| High | A share referencing only a mutable permission ID could silently gain fields or operations after an edit. | Bind shares to a permission ID and revision; edits make old shares inert until renewed. Normal role references still follow live edits. Section 3. |
| High | A team holding a manager role lets its membership editor acquire policy-administration powers indirectly. Delegation authority was insufficiently explicit. | Protected administrative assignments accept users only. Publish a fixed assignment-authority matrix; reserve team recipients for business roles. | High | CRUD and advanced App behavior were scheduled before the App credential boundary. Temporary reuse of admin cookies would undermine the intended separation. | Implement purpose/state checks, App context, inheritance and ceilings in milestone 2, before exposing data routes. | High | Returning a mutated entity could disclose unreadable fields to a caller with update/create rights but no read rights. | Writes return submitted IDs/revisions only. Returning entity fields requires a separate authorized read. Section 3. |

Existing provisioning fencing is not automatically an entity-publication protocol. | Immutable job manifest, one pending version, pinned physical-database lock, expected-version/attempt checks and registry compare-and-swap before activation. Reconcile physical state after interruption. Section 5. |
| High | The launch handshake omitted enough details to leave replay, App substitution, old-origin reuse and logout behavior ambiguous. | Bind nonce, S256 challenge, actual frame/window, origin and generation; consume launch codes transactionally; separate pending/active credentials; bind child tokens to an active issuing console session. Sections 4 and 7. |
| High | An optional App restriction can be removed by its App manager. Treating that restriction as a Space security boundary would permit widening. | Space-owned ceilings are mandatory; App-owned gates are optional restrictions within them. | High | New owner/team values, grant-recipient lookup, stale shares and deletion lacked complete lifecycle semantics. | Explicit ownership fields, update plus delegation authority for transfer, transactional share clearing/deletion, active recipients and permission-revision checks. Existing shares survive grantor-role removal by explicit design. Section 3. |
| High | Preflight reference/uniqueness checks alone race; shared entities referencing private App rows can cross the intended App boundary. | Composite local foreign keys with RESTRICT, database-enforced uniqueness, target-ID authorization, bounded deterministic locking and publication dependency rules. Shared-to-private and cross-App private references are rejected. Sections 5 and 6. |
| Medium | The proposal assumed deployed customers and introduced unnecessary role mapping, maintenance cutovers and compatibility machinery. Lastapp has no deployed installation. | Update the initial development schema/bootstrap and seed fixtures directly; replace affected APIs/callers together. Use a fresh local registry as needed, preserving unrelated local data. No legacy converters or production cutover plan. Sections 9–11. |
| Medium | A last-administrator count without serialization permits two concurrent removals to both succeed. Nullable composite foreign keys can also bypass intended scope checks. | Short transactions serialize the affected administrative scope; constraint branches explicitly require non-null columns. Direct invalid-insert and concurrent-removal tests are required. Sections 2, 4 and 12. |
| Medium | Request limits alone do not bound generated policy SQL, actor team sets, counts or connection demand. A centralized registry is a real capacity dependency. | Bound expanded authorization, SQL parameters, work/lock time and admission queues; batch registry loads; close registry snapshots before business I/O; share/evict pools with per-resource/process budgets. Counts are explicit. Sections 6 and 9. |
| Medium | Online additive DDL can block traffic or occupy the provisioning worker; DDL failure is not transaction rollback. | Small separate schema concurrency budgets, explicit algorithm/lock/time limits and ownership-based recovery for business-entity publication. No zero-downtime guarantee. Section 5. |
| Medium | Browser numbers, defaults, nulls, trailing spaces, decimals and timestamps can diverge between a JavaScript client, evaluator and MariaDB. Unbounded schema references can also cause validation work or remote fetches. | Safe-integer wire range, decimal strings, canonical times, explicit no-pad comparisons/null semantics, bounded local schema resolution and rejected unsupported constructs. | Medium | Broad App directory/metadata/capability responses or audit values could leak information outside entity row permissions. | Minimal self/team context, no general App Tenant roster, caller-authorized metadata, protected share rosters and business audit containing IDs/changed-field metadata rather than field values. Sections 1, 4 and 7. |

## Security and scaling limits retained explicitly

- Policy administrators can explicitly grant themselves business access. Administrative status alone grants no data, but this is governance power rather than separation from an immutable external authority.
- All micro-app code inside one App shares that App’s authority. Browser isolation protects other Apps/admin credentials; it cannot prevent an author exporting data deliberately entrusted to their App.
- Registry revocations apply to subsequent authorization snapshots. A bounded request already authorized may finish; local share/write ordering uses the parent-record lock. There is no distributed transaction or instant cancellation promise.
- A uniqueness/reference conflict may reveal existence of a value/dependency. Generic errors hide details but do not remove this inherent signal or all timing inference.
- A shared database and shared service credentials provide API isolation, not a security boundary against a compromised runtime or an external database owner. Dedicated deployment is a separate infrastructure choice.
- Scaling depends on registry read capacity, business-database capacity and explicit process/connection/work limits. The framework does not promise infinite scaling or an automatically optimal SQL compiler.

These are defined product boundaries, not unresolved alternatives hidden behind implementation work. The first phase deliberately excludes arbitrary backend code, external integration execution, general directory exposure, complex joins/aggregates/search, destructive migrations and the full generated-code runner.

## Implementation alignment and review validation

Read the complete proposal and the existing role/authentication handlers, SQL constraints, fixed action catalog, membership mutations and provisioning lock/credential paths. The current code still has Tenant-owned custom management roles, direct permission grants and flattened Space/App scopes; it has no generic business-entity executor. The plan identifies the required replacements in section 9 and preserves the existing provisioning/security/UI changes.

Primary references checked: [JSON Schema Draft 2020-12](https://json-schema.org/draft/2020-12), [MariaDB implicit commits](https://mariadb.com/docs/server/reference/sql-statements/transactions/sql-statements-that-cause-an-implicit-commit), and [MariaDB FOR UPDATE](https://mariadb.com/docs/server/reference/sql-statements/data-manipulation/selecting-data/for-update). They support the schema vocabulary and transaction cautions; they do not validate the proposed authorization implementation.

This review changes only the proposal and this review record. Static checks cover local document links, section structure and the policy example’s JSON syntax. No runtime tests, database changes, driver changes or server-version experiments form part of this review. The acceptance matrix specifies the implementation tests required for the completed local system.
